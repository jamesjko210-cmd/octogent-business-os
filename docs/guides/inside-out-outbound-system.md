# Inside-out Outbound System

Use this workflow when a tentacle needs validation, customer discovery, outreach, partner mapping, or follow-up without turning Octogent into a generic CRM.

The operating principle is simple: outbound should start from the inside of the project.

Generic outbound starts with third-party lists and templates. Inside-out outbound starts with the project's own evidence:

- closed-won or successful outcomes, when they exist
- real user feedback and interview language
- analytics, behavior logs, and support notes
- BMC assumptions and positioning decisions
- Notion decisions, research briefs, and source indexes
- known communities, schools, creators, partners, and warm relationships

## Workflow

1. **Gather internal proof**
   Read the relevant tentacle context, BMC notes, memory, research brief, user feedback, and analytics before drafting anything.

2. **Define best-fit signals**
   Convert evidence into a scoring rubric. Example signals: target age, mobile-first behavior, low-barrier access need, school/community fit, region, device constraints, and willingness to test.

3. **Score candidates**
   Score accounts, users, schools, communities, creators, or partners with explicit evidence. Keep assumptions separate from confirmed facts.

4. **Generate sequences from real language**
   Draft outreach from customer words and observed pain points. Avoid generic sales phrasing unless it matches the brand voice.

5. **Map warm-intro paths**
   Look for safe, approved relationship paths through school, friends, communities, GitHub, Gmail, Notion, or existing social channels. Do not expose private relationship data outside the task.

6. **Escalate only what needs the operator**
   Agents may rank, draft, summarize, log, and prepare follow-ups. The operator approves sends, public posts, partnerships, purchases, and sensitive replies.

7. **Log results**
   Store response quality, objections, language snippets, and next actions in Notion or local memory so the next sequence improves.

## No-key mode

Default to no API keys. Use logged-in apps, manual browser workflows, local files, Notion, Gmail/Drive connectors when available, and explicit handoff logs.

## Game-business example

For the game-as-business project, this workflow should not start by buying a broad "kids gaming" contact list. It should start by scoring small validation channels:

- younger sibling and nearby student feedback
- school peers who can test a 10-second game loop
- teachers or clubs that can safely observe testing
- small creators who show casual mobile games
- communities where lightweight free browser games are shared
- future NGO/school partners only after basic retention evidence exists

The first goal is not selling. The first goal is learning whether the game is instantly understandable, accessible, and replayable for the target segment.
